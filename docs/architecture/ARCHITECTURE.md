# Fin Nest 技术架构与协作约束

版本：v0.4  
状态：架构基线，所有未明确标注为 v1 之外的内容均按本文执行  
目的：让参与的 agent 或开发者在同一技术方向上推进，避免过早微服务化或把业务逻辑散落到前端页面中。

## 0. 原型来源与功能基线

当前功能基线来自 `claude-design/记账本.dc.html`，不是 `记账本-standalone-src.html`。agent 分析功能时必须优先读取 `记账本.dc.html`。

`记账本.dc.html` 是 Claude Design 导出的单文件交互原型，包含 UI、状态样例和部分业务逻辑。它只能作为产品功能和交互参考，不能直接复制为生产代码。原因是原型把所有页面、状态和逻辑塞在一个组件里，且局部存在旧版本拼接痕迹，正式工程必须重新做模块化设计、数据模型和一致性规则。

新版原型确认要做的功能模块：

- 账号与会话：登录、注册、登出，原型内置 demo 用户和本地会话；正式实现用户需包含别名字段。
- 多账本：账本列表、账本详情、新建/编辑/删除、切换账本、成员、邀请码申请加入、分享码弹窗、移除成员；加入申请需账本持有人审批。
- 账单首页：月度收支汇总、预算进度、按日期分组交易列表、月份选择、筛选状态。
- 交易详情：查看记录、编辑记录、删除记录、展示账户/成员/记录人/关联保单/关联物品/附件。
- 新增/编辑记账：支出、收入、转账；金额、分类、账户、日期、人员、备注、附件、可收回、需归还、关联保单、关联物品。
- 记账设置：配置记账表单字段顺序、字段可见性、账户/人员是否必填、金额小数位。
- 分类与人员：收入/支出分类、二级分类、图标、人员管理。
- 筛选：分类、时间、账户、人员、记录人、金额范围、备注关键词。
- 统计：支出/收入切换、分类占比、分类下钻、近 6 个月趋势。
- 计划：支出限额、收入目标、金额/次数指标、周期、详情、历史周期、命中明细、待确认开关。
- 预算：账本月度总预算、分类月度预算、账单首页预算进度（已用/剩余/百分比）；按当月有效支出计算，是独立于计划的滚动月度预算。
- 账户：净资产、储蓄/信用/投资/可收回/需归还、子账户、余额修改、资金变动、关联记录。
- 自动记账：自动规则列表、详情、新建/编辑、启用停用、删除、重复周期、下次记账、生成待确认记录、可收回/需归还关联。
- 快捷记账：快捷模板管理、详情、新建/编辑、从账单闪电入口选择模板、预填金额、可选直接记账。
- 保险管理：保险列表、详情、新建/编辑、终止、保单附件、被保人、保额、保费、缴费频率、续费方式、生效/到期。
- 物品管理：物品列表、详情、新建/编辑、附件、购买价、购买日、预期寿命、关联交易、耗材/维护记录、报废/取消报废。
- 文件附件：交易附件、保单附件、物品附件，原型用本地 URL 表示，正式实现走 MinIO。
- 提醒红点：v1 不做站内提醒中心，只在主 Tab 和更多页菜单入口显示红色圆圈提醒数量。
- Toast 与移动端交互：底部 sheet、左滑操作、滚轮日期/月选择器。

以上都属于产品范围，不能再按旧版原型把登录、多账本、保险、物品、自动记账视为后置探索。v1 不做的能力会在本文中明确标注。

## 1. 架构结论

Fin Nest 是一个 Docker 部署的 Web 应用，采用前后端分层架构：

- Web：Next.js，负责用户界面、交互体验、PWA 能力和少量 BFF 聚合。
- API：Nest.js，负责核心业务逻辑、权限、数据一致性、文件与 AI 编排。
- Worker：Nest.js 同代码库的后台进程，负责异步任务。
- 数据库：PostgreSQL，作为主业务数据存储。
- 对象存储：MinIO，用于票据、附件、分享图片等；v1 之后用于导出文件。
- 部署：Docker Compose。

明确不做微服务。Nest.js API 与 Worker 可以是同一个后端项目的不同启动模式，而不是多个独立服务。

个人/家庭自部署场景下，v1 不引入 Redis。后台任务、任务状态、幂等控制、轻量锁和必要缓存使用 PostgreSQL 实现，降低 Docker 部署和维护复杂度。

接口契约采用 Nest.js REST + OpenAPI。数据库访问采用 Prisma + Prisma Migrate，必要的 PostgreSQL 特性通过 raw SQL migration 补充。

## 2. 为什么需要 Nest.js 后端

当前原型功能不是简单 CRUD，已经包含：

- 多账本、多成员、邀请和权限。
- 交易、账户、转账、可收回、需归还等强一致业务。
- 计划、预算、统计和自动记账规则。
- 快捷记账模板、记账字段设置、交易详情与编辑。
- 保险、物品资产、附件、分享。
- AI 识别、AI 分类、自然语言记账、消费洞察属于 v1 之后能力。
- 后台任务、任务状态、幂等、轻量锁。
- MinIO 上传、访问控制、文件生命周期。

这些逻辑如果全部放在 Next.js Route Handler 或 Server Actions 中，后期容易变成页面、接口、任务和权限混杂。Nest.js 应作为业务中枢，保证规则集中、可测试、可复用。

## 3. 服务边界

### 3.1 Next.js Web

职责：

- 页面路由与移动端 Web UI。
- Liquid Glass 风格组件体系和移动端 PWA 体验。
- PWA 安装、响应式布局、移动端交互。
- 登录态展示和前端权限感知。
- 调用 Nest.js API。
- 处理乐观更新、前端缓存和表单状态。
- 必要时做轻量 BFF 聚合，但不承载核心财务规则。

不应负责：

- 账户余额最终计算与落库。
- 多成员权限最终判断。
- AI key 调用与模型编排。
- MinIO 直接凭证管理。
- 后台任务生产/消费的核心逻辑。
- 自动记账、计划命中、预算统计等复杂业务规则。

### 3.2 Nest.js API

职责：

- Auth、用户、账本、成员、权限。
- 交易、分类、人员、账户、计划、预算、保险等领域逻辑。
- 账户余额、转账、可收回、需归还的一致性处理。
- 筛选、统计、聚合查询。
- 文件上传签名、附件元数据。
- 提醒红点计数聚合。
- AI 任务创建、模型调用编排、结果落库。
- PostgreSQL 任务入队、任务状态、幂等键和轻量锁。

API 应保持模块化单体，而不是微服务。模块之间通过应用层服务调用，不通过 HTTP 调用自己。

### 3.3 Nest.js Worker

职责：

- 消费 PostgreSQL 任务表。
- 处理 AI 票据识别、自然语言解析。
- 处理周期账单、自动记账、提醒计数相关后台任务。
- 处理统计预计算、缓存刷新等后台任务。

Worker 与 API 共享领域代码、数据库模型和配置，但作为单独进程运行，便于扩缩容和隔离长任务。

## 5. 数据与基础设施选型

### 5.1 PostgreSQL

用途：

- 用户、用户别名、账本、成员、加入申请、权限、邀请/分享码。
- 交易、分类、人员、账户、计划、预算、保险、物品。
- 自动记账规则、快捷记账模板、记账设置。
- 附件元数据。
- AI 任务记录和结构化结果。
- 后台任务队列、任务状态、重试记录。
- 幂等键、轻量锁、审计日志。
- 审计日志和操作记录。

要求：

- 财务相关写入必须在事务中完成。
- 金额字段使用固定精度整数存储，数据库列使用 `amount_micros BIGINT`，代码中映射为 `amountMicros`；所有金额统一按 1,000,000 倍缩放保存，不使用浮点数存储。
- 记账设置中的金额小数位只控制输入校验和展示格式，不改变数据库金额存储精度。
- TypeScript 层金额不得用 `number` 承载精确计算，使用 `bigint`、字符串或 Decimal 工具封装。
- 重要业务表保留 `createdAt`、`updatedAt`，必要时保留 `deletedAt` 软删除。
- 多账本数据表必须包含 `ledgerId` 或能明确关联到账本。
- 后台任务使用自建 `background_jobs` 表和 PostgreSQL 锁实现。
- 自动记账、AI 等任务必须可重试，并记录失败原因；导入导出属于 v1 之后能力。
- 自动记账防重复使用唯一约束和幂等键。

### 5.2 Redis

v1 不启用 Redis，也不作为 Docker Compose 必需服务。

Redis 加入条件如下；达到条件前不加入：

- 需要 BullMQ 这类成熟 Redis 队列。
- AI 或 v1 之后导入导出任务量明显增大，PostgreSQL 队列成为瓶颈。
- 需要 WebSocket pub/sub、实时协作或更复杂的分布式通知。
- 从家庭自部署演进到多租户公开服务，需要统一限流和热点缓存。

v1 之后如加入 Redis，PostgreSQL 仍然是主事实来源；涉及金钱和账户状态的最终结果必须落 PostgreSQL。

### 5.3 MinIO

用途：

- 票据图片。
- 交易附件。
- 保险附件。
- 物品附件。
- v1 之后导出文件。
- 分享图片或报表快照。

要求：

- 数据库只保存对象 key、bucket、mime、size、owner、ledgerId、业务关联 id。
- 客户端上传应优先使用后端签发的临时上传 URL。
- 文件访问权限必须由 API 控制，不允许用户猜 key 直接访问私有文件。
- 对象 key 必须包含账本、业务类型、业务对象、日期和随机段，避免冲突和泄露原始文件名。
- 删除交易、保单、物品等业务对象时，同步删除其附件元数据，并删除 MinIO 对象；删除失败必须记录待清理任务。

## 6. 领域模块边界

模块划分：

- AuthModule：登录注册、会话、用户身份。
- UserModule：用户资料、用户别名。
- LedgerModule：账本、成员、邀请、加入申请、角色。
- TransactionModule：支出、收入、转账、交易详情、交易编辑、交易附件、交易查询。
- CategoryModule：收入/支出分类、二级分类。
- PersonModule：账本内人员。
- AccountModule：储蓄、信用、投资、可收回、需归还、子账户、余额调整。
- StatsModule：分类统计、趋势、聚合。
- PlanModule：支出限额、收入目标、周期计算、命中明细。
- BudgetModule：代码可并入 PlanModule，但数据模型独立。负责账本月度总预算、分类月度预算、账单首页预算进度，不复用 `plans` 表，不存历史周期。
- RecordSettingsModule：记账字段排序、字段显隐、账户/人员必填设置。
- AutoAccountingModule：自动记账规则、重复周期、启用停用、下次生成。
- QuickAccountingModule：快捷记账模板、一键记账、模板预填。
- InsuranceModule：保险管理。
- ItemModule：物品资产、购买信息、预期寿命、报废、关联交易。
- FileModule：MinIO 文件与附件。
- ExportModule：v1 不实现；导入导出能力进入 v1 之后规划。
- AiModule：v1 不实现；自然语言记账、票据识别、分类推荐、消费洞察进入 v1 之后规划。
- ReminderModule：红点提醒计数聚合，不做站内提醒中心。

模块可以在同一个 Nest 应用内互相调用服务，但必须避免循环依赖。涉及跨模块写入的流程应由明确的应用服务编排。

## 7. 核心业务一致性原则

- 交易写入、账户余额变更、可收回/需归还变更必须在同一个数据库事务中完成。
- 交易必须区分原始金额和有效统计金额。列表展示、收支统计、计划命中默认使用有效金额；账户余额变动使用原始现金流金额。
- 可收回/需归还关联会从原始金额中扣减，形成有效金额；关联金额合计不能大于交易原始金额。
- 四种关联方向都遵循同一有效金额扣减规则：支出计入可收回、收入产生需归还、支出冲减需归还、收入冲减可收回。
- 支出计入可收回、收入产生需归还会增加对应项目余额；收入冲减可收回、支出冲减需归还会减少对应项目余额，且不能把项目余额扣成负数。可收回/需归还账户页不再提供独立收款/还款入口，若需修正项目余额，统一走余额调整并生成调整记录。
- 支出/收入是否必须绑定账户由账本的记账设置决定；账户默认非必填。
- 当支出/收入绑定账户时，保存交易必须立即改变账户或子账户余额；未绑定账户时只记录收支事实，不影响账户余额。
- 转账必须立即改变两个账户或子账户余额，并保留转账流水。
- 编辑交易时必须用反向账户流水回滚旧交易造成的账户影响，再应用新交易影响。
- 删除交易时必须用反向账户流水回滚该交易造成的账户影响和派生资金变动。
- 手动修改账户或子账户余额必须生成独立账户调整记录，调整记录可查询、可审计，不允许静默覆盖余额。
- 删除分类、人员、账户前必须定义历史交易策略，不能导致历史记录无法展示。
- 分类只要存在关联交易，就不能删除；如需隐藏，应使用停用/归档。
- 人员只要存在关联交易，就不能删除；如需隐藏，应使用停用/归档。
- 交易可以关联保单、物品、附件、可收回/需归还项目；编辑或删除交易时必须同步反向处理相关派生资金变动。
- 可收回项目属于资产，需归还项目属于负债。
- 账户是否计入净资产由 `excludeFromTotal` 控制。
- 账本是核心隔离边界。交易、分类、人员、账户、计划、自动规则、快捷模板、保险、物品、附件都必须归属到账本。
- 成员权限必须在 API 层做最终判断。前端只能做显示和交互优化。
- 账本 owner 和 member 的业务权限基本一致；member 可以查看、新增、编辑、删除账本内业务数据，也可以修改他人记账，但不能删除账本。
- 删除账本仅 owner 可执行。
- 交易必须记录创建人和最后修改人；修改他人记账时必须保留修改人、修改时间和审计记录。
- 邀请码/分享码必须有创建者、所属账本、有效期、使用记录和撤销能力，默认有效期为 1 天。
- 用户通过邀请码只创建加入申请，不会直接成为账本成员；必须由账本 owner 同意后才正式加入。
- 自动记账不直接入账，只生成待确认记录；用户确认后才进入正式交易。
- 自动记账只保证同一规则同一次调度不重复生成，不判断用户是否已经手动记录了同周期同内容交易，由用户在待确认列表中判断是否确认或删除。
- 快捷记账模板只生成草稿或交易，不能绕过交易服务的一致性规则。
- 快捷记账字段边界与直接记账一致。开启“直接记账”时，除日期外的所有必填字段必须已在模板中填写；日期使用触发当天。
- 保险和物品本身不是账户，但它们可以被交易关联，并参与查询、汇总和红点提醒计数。
- 统计结果可以缓存，但缓存不是事实来源。
- 所有关键写操作应支持幂等，尤其是 AI 任务回写、自动记账、周期账单生成。

## 8. Token 与外部系统认证

v1 使用数据库托管的 opaque session token，不使用纯 JWT 作为登录态。

首次启动时，第一个注册用户自动成为系统管理员。系统管理员可以在设置中控制是否开放注册；关闭注册后，除管理员创建/邀请外，普通用户不能自行注册。

用户登录流程：

1. 用户通过账号/邮箱 + 密码登录。
2. API 生成高强度随机 session token。
3. 明文 token 只返回给客户端，优先写入 `HttpOnly`、`Secure`、`SameSite` Cookie。
4. 数据库只保存 token hash，不保存明文 token。
5. 每次请求 API 根据 token hash 查询 session 是否存在、未过期、未吊销、用户未禁用。

这样必须支持：

- 立即吊销某个设备的 session。
- 立即吊销某个用户的全部 session。
- 修改密码后吊销历史 session。
- 禁用用户后所有 session 立即失效。
- 权限变化不依赖 token 过期时间，API 每次按当前用户、账本、成员关系判断。

核心表：

```txt
users
- id
- email
- account
- alias
- isAdmin
- passwordHash
- disabledAt
- createdAt
- updatedAt

sessions
- id
- userId
- tokenHash
- deviceName
- userAgent
- ip
- expiresAt
- revokedAt
- lastSeenAt
- createdAt

service_tokens
- id
- name
- tokenHash
- scopes
- allowedIps
- expiresAt
- revokedAt
- lastUsedAt
- createdAt
```

用户字段说明：

- `email`：登录凭证和通知地址。
- `account`：登录账号，唯一；v1 不提供账号名修改功能。
- `alias`：用户别名，用于界面展示、成员显示、审计显示，可以修改。
- `passwordHash`：密码哈希，禁止保存明文密码。

外部系统，例如 v1 之后 AI 功能接入 Dify，不使用用户登录 session token。外部系统必须使用独立的 service token：

```txt
Authorization: Bearer fn_svc_xxx
```

service token 要求：

- 数据库只保存 hash。
- 可随时吊销。
- 可设置过期时间。
- 可设置 scopes。
- 支持 allowed IPs；未配置时不限制来源 IP。
- 每次调用记录 lastUsedAt 和审计日志。

service token scopes：

- `users:read`
- `ledgers:read`
- `transactions:read`
- `transactions:write:draft`
- `ai:write`
- `files:read`

如果外部系统需要“代表某个用户”操作，不得保存用户 session token。应使用：

```txt
service token + actorUserId + ledgerId + scope
```

API 必须校验：

1. service token 有效且未吊销。
2. service token 具备对应 scope。
3. `actorUserId` 存在且用户未禁用。
4. `actorUserId` 对 `ledgerId` 有对应权限。
5. 写操作必须记录审计日志，标记来源为 service token / Dify。

## 9. AI 功能预留

AI 不应直接耦合到页面组件中，应作为后端能力存在。

AI 属于 v1 之后功能。v1 只保留模块边界和认证预留，不实现 AI 数据模型和接口。

初期 AI 场景：

- 自然语言记账：例如“昨天午饭花了 32，用支付宝”，解析为交易草稿。
- 票据识别：上传图片后识别金额、商户、时间、分类推荐。
- 自动分类推荐：根据备注、金额、商户和历史习惯推荐分类。
- 保单信息提取：从保单附件中提取险种、保额、保费、期限、被保人。
- 物品信息提取：从购物凭证或发票中提取物品名称、价格、购买日期、保修/寿命推荐。
- 消费洞察：生成月度总结、异常消费提醒、预算推荐。
- 自动记账辅助：识别周期账单或重复消费。

AI 架构原则：

- Web 创建 AI 任务或请求草稿结果。
- API 负责鉴权、限流、任务创建、模型调用封装。
- 长耗时任务进入 PostgreSQL 任务表，由 Worker 执行。
- AI 输出先作为草稿，关键财务记录由用户确认后落库。
- 保存原始输入、模型结构化输出、用户确认结果，用于 v1 之后优化。
- 模型 key 和供应商配置只存在服务端。

## 10. Docker 部署形态

开发与部署包含以下容器：

```txt
web       Next.js
api       Nest.js HTTP API
worker    Nest.js Worker
postgres  PostgreSQL
minio     MinIO
proxy     Nginx
```

部署原则：

- 使用环境变量配置服务连接。
- API 和 Worker 共享同一套数据库迁移。
- 数据库迁移应作为显式步骤执行，不在多个容器启动时并发执行。
- MinIO bucket 初始化可以由一次性 init 容器或脚本完成。
- 本地开发优先使用 Docker Compose 拉起依赖服务。
- v1 Compose 不包含 Redis。

## 11. 接口、ORM 与初始化

接口采用 REST + OpenAPI：

- Nest.js Controller 必须维护 OpenAPI 注解。
- 前端类型通过 OpenAPI 生成；共享 DTO/schema 只用于跨端常量和校验工具。
- API 错误结构必须统一。
- 外部系统使用 REST API + service token + scope，不使用用户 session token。

ORM 采用 Prisma：

- 使用 Prisma 作为主要 ORM。
- 使用 Prisma Migrate 管理迁移。
- `citext`、复杂索引、必要 check constraint 等 PostgreSQL 特性可通过 raw SQL migration 补充。
- v1 不使用 TypeORM。
- 财务写操作必须使用 Prisma transaction。
- API 和 Worker 不得在启动时并发自动执行迁移，迁移必须作为显式步骤。

初始化规则：

- 第一个注册用户自动成为系统管理员。
- 第一个用户注册成功后，自动创建默认账本、owner membership、默认记账设置、默认人员“我”、基础收入/支出分类。
- 不自动创建默认账户，因为账户默认非必填，账户类型和初始余额更适合用户自己决定。
- 新建账本时也自动创建默认记账设置、默认人员“我”、基础收入/支出分类。
- 初始化逻辑必须幂等。

提醒规则：

- v1 不做站内提醒中心、已读未读、推送、邮件或短信。
- 提醒只显示为主 Tab 和更多页菜单入口上的红色圆圈数字。
- 后端提供 `GET /ledgers/:ledgerId/reminder-summary` 聚合计数。

导入导出：

- v1 不做导入导出、备份恢复、附件打包、导出文件生成。
- v1 之后实现导入导出时，必须单独设计数据一致性和权限边界。

## 12. 前端实现原则

- 移动端优先，先实现 Web/PWA，不做原生 App；PC 端第一阶段只居中展示移动端容器。
- 页面应围绕业务模块拆分，不复刻原型中的单个大组件。
- `claude-design/记账本.dc.html` 只作为交互和功能参考，不作为可复用源码。
- 表单使用统一校验 schema，尽量与后端 DTO 共享类型。
- 列表、筛选、统计需要考虑乐观更新与缓存失效。
- 金额展示统一格式化，内部统一金额单位。
- 图表优先轻量实现，避免过早引入重型可视化框架。
- UI 方向为 iOS Liquid Glass 风格，但不要把设计稿 HTML 直接搬进生产代码。
- `liquid-glass-react` 可以作为底层玻璃效果库，但必须经过项目自有 `components/glass` 封装后使用，业务页面不得直接依赖该库。
- 同屏大量重复内容，例如交易列表行，不应滥用重玻璃效果；玻璃效果优先用于 Tab Bar、Bottom Sheet、浮动按钮、菜单、筛选面板等关键容器。
- 前端详细约束见 `FRONTEND_DESIGN.md`，前端工程规范见 `FRONTEND_ENGINEERING.md`。

## 13. 后端实现原则

- Controller 只处理 HTTP 入参、鉴权上下文和响应，不写业务规则。
- API 契约使用 REST + OpenAPI。
- ORM 使用 Prisma，迁移使用 Prisma Migrate + 必要 raw SQL migration。
- Service 负责业务编排。
- Repository 或 ORM 层负责数据访问。
- DTO 必须校验。
- 登录 session 和 service token 都必须只存 hash。
- 用户认证使用 opaque session token；外部系统使用 service token + scope。
- 财务写操作必须使用事务。
- 跨模块流程由应用服务编排，不让数据库触发器承载核心业务。
- 后台任务必须记录任务状态、错误信息和重试次数。
- 重要操作预留审计日志。
- 后端详细工程规范见 `BACKEND_ENGINEERING.md`。

## 14. 测试策略

- 涉及交易、账户、权限、token、初始化逻辑时，必须同步写后端测试。
- 后端测试重点覆盖财务一致性、Prisma 事务、权限边界、session/service token 失效。
- 前端测试重点覆盖金额输入、筛选复用、Sheet 栈、附件预览、红点计数和 `/__dev/ui`。
- 测试详细约束见 `TESTING_STRATEGY.md`。

## 15. 不做的事

当前阶段明确不做：

- 不拆微服务。
- v1 不引入 Redis 或独立消息中间件。
- 不做多客户端原生架构。
- 不把 AI 逻辑写进前端页面。
- 不让 Next.js 直接访问数据库承担核心业务。
- 不使用不可立即吊销的纯 JWT 作为主登录态。
- 不让外部系统保存或复用用户登录 session token。
- 不把 MinIO 设置为公开桶来绕过权限控制。
- 不为了原型还原而牺牲数据模型和业务一致性。
- 不使用 GraphQL/tRPC 作为 v1 主接口契约。
- 不使用 TypeORM。
- v1 不做导入导出、备份恢复或附件打包。
- v1 不做站内提醒中心、已读未读、推送、邮件或短信。
